## Reviewer workflow

1. Select a node. Inspect the existing tags and linked parent ways. Use the JOSM or OSM links to inspect the exact crossing and road arm. Parent-way context is from the original audit; download current surroundings in JOSM.
2. Enter only verified changes. Keep means leave the current tag untouched; Remove means remove that one tag. All other tags and the coordinates remain unchanged. The marked/unmarked presets are per-object drafts, never approvals. No group-wide approval or majority vote is supported.
3. Record your OSM username/name, evidence (survey notes or permitted imagery URL and date), observation date, and source type. Confirm source permission, exact arm and connected node/way consistency. Unknown is not no. Do not call an amber flasher a pedestrian traffic signal solely because it has a button.
4. Mark that item reviewed. Repeat for a small batch; 1–5 related nodes is a useful first pilot. Save review decisions as JSON to resume or hand off. Importing saved decisions validates object versions again at export. Data is otherwise held in this browser page only.
5. Record any applicable community-review reference. For individual manually reviewed work, briefly state why wider automated/import review is not applicable. Confirm the applicable process has been completed. This checkbox does not create permission or replace community discussion.
6. Export reviewed .osm. The page reads the public OSM API immediately before export; it never logs into OSM and never uploads. It stops the whole export if an object version, coordinate or tag differs, a decision is incomplete, or a contradiction remains. If a browser blocks the public API request, use the supplied snapshots and complete review directly in JOSM; there is no unchecked-export fallback.
7. In JOSM: File > Open the .osm, download surrounding data and current objects, resolve conflicts, inspect every modified object, run Validator, and supply a precise changeset comment and actual evidence sources. JOSM uploads the reviewed changes together. Do not blindly merge layers already edited in another copy. The .osc is for editor interchange; direct API uploading additionally needs a newly opened changeset ID and authorization, which this tool deliberately does not provide.

The exported nodes have positive existing IDs, the checked versions, original coordinates, complete tags and modification actions. No deletions, new POIs, road geometry, ways or relations are generated by this first editor. The nine site snapshots support those more complex edits in JOSM, where real topology can be reviewed. A modified crossing node may require corresponding way edits; do those together in JOSM before upload.

## Defining a similar crossing

Use the same jurisdiction and a matching combination of road class, intersection form (T/four-arm/roundabout), carriageway layout, lane count, refuge islands, crossing connection, markings, pedestrian signal type, amber flashers and current installation state. Confirm the exact arm. Do not transfer access, kerb, tactile paving, signal, marking or wheelchair values merely from a nearby example.

The generated groups use only available OSM attributes (conflict type, parent road class and lane count, recorded markings/island/signals/flashers). Intersection form and divided-road structure are not automatically classified. Missing attributes remain unknown. Consequently these groups are less strict than the physical definition and must never be described as 99% matches. Existing OSM tags are themselves under review and cannot serve as independent evidence that the same tags are correct elsewhere.

Useful further surveys: kerb ramps and tactile paving on their actual kerb nodes; refuge islands; sidewalk connectivity; pedestrian signal and amber-flasher type; bicycle parking capacity/type; EV station grouping/connectors/access; washroom operation and accessibility. Each field needs site-specific evidence. Planned projects and closed facilities stay separate from existing open infrastructure.
